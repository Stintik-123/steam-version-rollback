# Version Rollback

> **Состояние на 17.11.2026 (версия 0.5.4), передача в работу**
>
> - Бэкенд собирается в один `backend/main.lua` и **работает**: `millennium.ready()` вызывается, RPC `ping` отвечает (`{"ok":true,"probe":"raw"}`).
> - **Известная проблема:** при включённом монтировании UI (`mountDock()` / `startBetasSection()`) Lua-хост падает с `0xC0000409 (Stack Buffer Overrun)` сразу после старта, и Millennium показывает кран-диалог. Поэтому оба вызова в `frontend/index.tsx` сейчас заменены на `void mountDock;` / `void startBetasSection;` — плагин грузится без падений, но своей кнопки в интерфейсе не показывает.
> - RPC идёт через `Millennium.callServerMethod(pluginId, method, kwargs)` — это единственный рабочий путь в этой сборке Millennium (глобального `backend` нет).
> - Что проверять дальше: минимальный репро-плагин, который монтирует пустой `<div>` через `SP_REACTDOM`, чтобы понять, что именно роняет хост: сам ReactDOM-мост, `document.body.append` или размер бандла.

Плагин Millennium для Steam: поставить конкретную версию игры вместо текущей.

Вы выбираете ветку (включая legacy-ветки разработчика) или вбиваете manifest GID
вручную — Steam сам скачивает нужные депо через свою же команду `download_depot`,
после чего плагин может подменить файлы игры, сделав бэкап старой версии.

Ничего не скачивается в обход Steam и вашего аккаунта: доступны только те депо,
на которые у вас есть лицензия.

| Слой | Состояние |

| Lua-бэкенд: парсинг VDF/ACF, план загрузки, очередь депо, бэкап и подмена файлов | написан, покрыт тестами (53 проверки) |
| Фронтенд: панель в настройках Millennium | написан, `tsc --noEmit` без ошибок |

| Хуки-патчи JS (`backend/patches.lua`) | каркас готов, якоря не подобраны — не используются, см. `docs/HOOKING.md` |

## Установка

Минимально нужен Millennium 3.x со starlight (проверялось на 3.6.3) и Node.js для сборки.

```powershell
cd version-rollback
npm install
npm run pack          # соберёт build/com.versionrollback.steam.star
```

Дальше либо скопировать `.star` в `C:\Program Files (x86)\Steam\millennium\plugins\`
(потребуется повышение прав), либо собрать сразу в установленный Millennium:

```powershell
npm run build         # output_path = "auto" в millennium.toml
```

После установки — перезапуск Steam, затем **Настройки → Millennium → Version Rollback**.

## Где это в Steam

Основное место — там же, где Steam сам показывает версии:

**Библиотека → правый клик по игре → Свойства → «Версии и бета-версии»**.

Внизу страницы появляется блок **Version Rollback** с тем же выбором версии и кнопкой
загрузки. AppID подставляется из открытой игры автоматически (если не получилось —
выберите игру в списке внутри блока).

Резервный вход — **Настройки → Millennium → Version Rollback**: та же панель целиком,
если вставка в свойства не сработала (например, Steam поменял вёрстку или язык
интерфейса не входит в список распознаваемых).

## Источники данных

| Источник | Что даёт | Ограничение |
| --- | --- | --- |
| api.steamcmd.net | текущие депо и манифесты веток | только «сейчас», без истории |
| SteamRaw (`/api/app/<id>/builds`, `/history`) | сборки и изменения `depots.<depot>.manifests.<branch>.gid` | история только с сентября 2026, без ключа, просят кэш и User-Agent |
| SteamCounts (`/app/<id>`, таблицы Updates и Depots) | датированные обновления (старая → новая сборка, ветка, changelist) и текущие GID по депо | публичного API нет: страница разбирается как есть; снимков манифестов старых сборок не даёт |
| локальный `appmanifest` | что реально стоит и куда качать | только текущая установка |
| локальный кэш (`logs/content_log.txt`, `steamapps/depotcache/*.manifest`) | какие манифесты Steam уже видел на этом компьютере — в том числе для сборок старше истории SteamRaw | только то, что осталось на диске; `content_log.txt` пишется не всегда |
| общая база версий (`resources/versions-db.json`) | сборки и снимки манифестов, накопленные заранее и дополненные локальным сбором | метаданные без ключей депо; пополняется вручную |
| SteamDB | глубокая история | только вручную: API нет, автопарсинг запрещён |

Как работает «История версий»: берём текущие манифесты ветки из AppInfo и откатываем их назад по изменениям из SteamRaw до времени выбранной сборки. Поэтому у старых сборок может стоять пометка «неполная» — история не доходит до их даты.

SteamCounts подключён как второй источник: он отдаёт датированный список обновлений с ветками и номерами changelist — независимая перекрёстная проверка SteamRaw и способ узнать, какие legacy-ветки (вроде `2_31_old`) существовали. Отдельно оттуда берутся текущие GID по депо — на случай, если `api.steamcmd.net` молчит.

В панели есть блок **«Источники данных»**: полный список подборки (18 пунктов) с пометкой, что подключено, что требует личного ключа, а что отключено сознательно, кнопка живой проверки доступности и загрузка из SteamCounts.

«Проверить локальный кэш» читает `logs/content_log.txt` и `depotcache` и показывает, какие манифесты Steam уже встречал на этой машине. Сборки из истории SteamRaw, чьи манифесты совпадают с локальными, помечаются «была на этом ПК», а любой найденный GID можно одной кнопкой отправить в план.

«Импорт из SteamDB» принимает вставленный текстом список «депо GID» — это ручной ввод, без обращения к SteamDB: понимает `1091501 2461377369266892508`, `1091501, 2461377…` и `DepotID 1091501 ManifestID 2461377…`.

Ключи депо и подобные «ускорители» в плагине не используются принципиально: скачивание всегда идёт через Steam и только для того, что есть на аккаунте.

## База версий

История SteamRaw начинается в сентябре 2026, а SteamDB парсить нельзя. Поэтому
плагин везёт с собой **общую базу версий** — только метаданные, без единого ключа депо:

- `resources/versions-db.json` — база, которая едет в `.star`. Формат: AppID → сборки
  (`buildid`, ветка, время) → набор `depotid → manifest GID`.
- Собирается скриптом `npm run db` (или `node tools/build-versions-db.mjs`) из
  SteamRaw (сборки + история AppInfo) и `api.steamcmd.net` (текущие манифесты).
  Список игр — в `tools/versions-db-apps.json`, можно менять и пересобирать:
  `node tools/build-versions-db.mjs 1091500 730`.
- `%LOCALAPPDATA%\VersionRollback\versions-db.json` — локальная копия: сюда попадает
  всё, что собрано на вашей машине; она имеет приоритет над общей базой.

Сборки из базы показываются в «Истории версий» вместе со сборками SteamRaw
и помечаются «из базы».

### Локальный сбор данных и отправка в Issue

SteamRaw не знает про версии старше сентября 2026, а такие версии иногда остаются
на компьютере: в `logs/content_log.txt`, в `steamapps/depotcache/*.manifest` и в
`appmanifest_*.acf`. Поэтому плагин умеет **собирать метаданные о версиях по максимуму**
и складывать их в локальную базу.

Где спросить разрешение: **в разделе «Библиотека» Steam**, а не в настройках плагина.
При выходе крупного обновления (сейчас 0.3.0) в библиотеке появляется баннер в правом
нижнем углу с выбором — «Да, собирать» / «Нет, не собирать». То же самое можно выбрать
в блоке «Версии и бета-версии» любой игры. В настройках плагина стоит только напоминание,
где принимается решение.

Что происходит при «да»:

- плагин обходит **все установленные игры** и по каждой собирает:
  - локальные кэши Steam (`content_log.txt`, `depotcache`, `appmanifest`);
  - сборки и восстановленные снимки манифестов из **SteamRaw** (по всем веткам);
  - текущие GID по депо из **SteamCounts**;
- всё складывается в `%LOCALAPPDATA%\VersionRollback\versions-db.json` (локальная база);
- формируется отчёт — только метаданные `AppID / buildid / depotid / manifest GID`,
  без аккаунта, machine-id и ключей депо;
- отчёт можно отправить в Issue проекта на GitHub:
  - **«Открыть Issue на GitHub»** — открывает предзаполненную форму (отправляете вы сами);
  - **«Создать Issue автоматически»** — если задан личный токен GitHub (кнопка «Создать
    токен на GitHub» ведёт на страницу выдачи токена).

Что происходит при «нет»: плагин не читает ни `content_log.txt`, ни `depotcache`,
ни `appmanifest`, не ходит в SteamRaw и SteamCounts и ничего никуда не отправляет.

Наружу само ничего не уходит: сетевые запросы плагина — это публичные AppID в SteamRaw
и `api.steamcmd.net`, а отправка отчёта — только по вашему нажатию. Решение хранится
в настройках Millennium (`collect_consent`, `consent_shown_for`) и переспрашивается
после каждого крупного обновления.

## Как пользоваться

1. Выберите игру из списка установленных (или введите AppID).
2. «Подтянуть» — плагин возьмёт депо и манифесты из `api.steamcmd.net` (кэш 6 часов).
3. Выберите ветку. Если нужной версии в ветках нет — включите «Свой manifest ID»
   и добавьте пары `depotid → GID` (SteamDB → Depots → Manifests).
4. Режим:
   - **Только скачать** — файлы лягут в `steamapps/content/app_<id>/depot_<id>`,
     игру никто не трогает. Безопасный вариант, чтобы сначала посмотреть.
   - **Скачать и подменить** — после успешной загрузки всех депо ставит файлы на
     место игры, предварительно переименовав текущую папку в бэкап.
5. «Скачать эту версию» → прогресс по депо → «Применить подмену файлов».
6. «Вернуть как было» — возвращает папку из бэкапа.

Игра **не обязана быть установлена**: `download_depot` работает по лицензии, а не по наличию файлов. Без `appmanifest` плагин сам выбирает библиотеку с максимумом свободного места и качает только в `steamapps/content` (режим подмены при этом недоступен).

Для игр без публичных веток (как CoD на вашем скриншоте) есть путь через manifest ID:
кнопка **SteamDB: депо** открывает нужную страницу, оттуда берётся `depotid` и `Manifest GID`.

## Ограничения, о которых лучше знать заранее

- **Старые манифесты может быть недоступны.** Valve отдаёт только те манифесты,
  которые разработчик оставил доступными; на закрытые ветки и снятые билды
  `download_depot` вернёт ошибку. Это ограничение Steam, а не плагина.
- **Прогресс приблизительный.** Steam не отдаёт прогресс `download_depot` наружу,
  поэтому плагин считает размер файлов на диске. Отметка «готово» — эвристика
  (99.5% ожидаемого размера или 25 секунд без прироста); есть кнопка «готово вручную».
- **Steam захочет обновиться обратно.** После подмены не запускайте обновление
  игры. Кнопка «Задержка автообновления» пробует `app_delay_update` — это
  экспериментальная команда клиента, поведение зависит от версии.
- **Сетевые игры и античит** могут не пустить на старую версию. Это не лечится.
- **Место на диске.** Подмена не копирует файлы (переименование в пределах тома),
  но бэкап старой версии остаётся на диске, пока вы его не удалите.

## Разработка

```powershell
npm run dev           # starlight watch: перезапуск бэкенда и UI при правках
npm test              # Lua-тесты под fengari (Lua 5.3 в JS)
npx tsc -p tsconfig.json --noEmit
npm run pack          # сборка .star в build/
```

Почему тесты на fengari, а не на `millennium.luavm64.exe`: последний — IPC-хост,
он ждёт подключения от Millennium и произвольные скрипты не исполняет. Тесты
подменяют `fs`/`utils`/`logger`/`json` заглушками, поэтому не трогают диск и сеть.

### Структура

```
backend/main.lua        точка входа, on_load/on_frontend_loaded/on_unload, патчи
backend/rpc.lua         RPC-поверхность для фронтенда (JSON-строки, pcall)
backend/patches.lua     хуки в UI Steam (по умолчанию отключены)
backend/lib/vdf.lua     парсер Valve KeyValues (VDF/ACF)
backend/lib/steam.lua   библиотеки Steam, appmanifest, папки депо
backend/lib/appinfo.lua api.steamcmd.net: депо, ветки, манифесты, кэш
backend/lib/steamraw.lua SteamRaw: сборки и история изменений AppInfo
backend/lib/localcache.lua локальный кэш Steam + разбор вручную вставленных GID
backend/lib/steamcounts.lua SteamCounts: датированные обновления и текущие GID
backend/lib/versiondb.lua  общая+локальная база версий: сборки и манифесты
backend/lib/collector.lua сбор по всем играм + отчёт для GitHub Issue
backend/lib/plan.lua    чистая логика выбора депо и манифестов
backend/lib/jobs.lua    очередь download_depot + измерение прогресса
backend/lib/swap.lua    бэкап, перенос файлов, откат
backend/lib/util.lua    пути, лог, JSON, форматирование
frontend/index.tsx      definePlugin + FFI-функция execConsole
frontend/ui/VersionPanel.tsx  панель
frontend/ui/ConsentBanner.tsx баннер выбора сбора данных в разделе «Библиотека»
frontend/inject.tsx     вставка панели в свойства игры + баннер в библиотеке
frontend/lib/rpc.ts     обёртки над backend.*
resources/labels.json   подписи веток (можно переопределить своим файлом)
resources/versions-db.json  общая база версий (сборки + манифесты), едет в .star
tools/build-versions-db.mjs  пересборка базы версий из SteamRaw и steamcmd.net
tools/probe-sources.mjs   живая проверка доступности всех источников из подборки
tests/                  Lua-тесты и фикстуры ACF/VDF
tools/probe.js          диагностика клиента в DevTools
docs/HOOKING.md         как подбирать хуки
```

Свой `labels.json` кладётся в `%LOCALAPPDATA%\VersionRollback\labels.json` и
важнее встроенного: `{ "1091500": { "2_31_old": "2.31 — до Phantom Liberty" } }`.
